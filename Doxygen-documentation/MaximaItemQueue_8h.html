Detailed Description

The hand-over of Maxima's output from the socket thread to the GUI (GH #2594).

The socket thread splits what Maxima sends into items (one XML tag, or a run of plain text) and the GUI thread works through them. Until GH #2594 every item became a wx event of its own, and wxWidgets handles all pending events before it looks at the keyboard, the mouse or a repaint again. A command that printed faster than wxMaxima could lay the output out, such as for i thru i+1 do disp(i), therefore kept that queue from ever running empty: nothing was drawn, and not even Ctrl+G got through.

So the items now wait in this queue, and the GUI thread takes them one by one, for a limited time per turn of the event loop (DrainForAtMost()). Two more rules keep a flood under control:

  • The consumer is only told about new items when it has run out of them (Push() returns true then). While it still has a backlog it comes back by itself, so the notifications can't pile up in the event queue either.
  • Once the backlog exceeds a limit, the socket thread stops reading (BackPressure()). Maxima then blocks writing to the socket, which pauses the calculation until the GUI has caught up, instead of wxMaxima buffering output without limit – it used to grow by hundreds of megabytes a minute.

Splits what Maxima sent into items.

An item is either a complete known XML tag (its start tag, its contents and its end tag), or the plain text between such tags. A newline directly after a tag's end belongs to the tag. A known tag whose end hasn't arrived yet stays in the buffer, as does everything after it – and so does a "<" at the very end that may turn out to start a known tag.

Parameters

How many characters at the start of buffer were handed on

Walks the buffer once. It used to cut each item off the buffer as it found it, copying the whole rest of the buffer each time, which made a buffer full of short items (disp() in a loop, GH #2594) quadratically slow to split.
